01

El modelo en una vista

Todo el módulo se articula sobre tres piezas: un árbol auto-referenciado que contiene menús y reportes, y dos relaciones N:M —usuario↔rol y rol↔nodo— que se resuelven con tablas puente. Las demás tablas sostienen a estas tres.

Lo que cambia frente al esquema heredado. SSOWS modela la navegación como cuatro tablas encadenadas (sistemas → secciones → subsecciones → modulos) y la tabla permisos arrastra las cuatro llaves foráneas a la vez. Eso fija la profundidad en cuatro niveles, obliga a un JOIN de cuatro tablas en cada lectura de menú y exige una fila de permiso por hoja. Aquí, la misma información vive en un árbol único.

03

El árbol: adyacencia como verdad, path como índice

La pregunta era lista de adyacencia o conjuntos anidados. La respuesta es que ninguna de las dos basta sola, porque el árbol tiene dos perfiles de uso opuestos: se escribe poco pero de forma desordenada —el administrador crea, renombra y sobre todo mueve carpetas de reportes— y se lee constantemente, una vez por cada sesión que se abre.

Coste de cada patrón sobre las dos operaciones que importan
PatrónLeer un subárbolMover un nodoIntegridad
Adyacencia pura Recursión en cada consulta UPDATE de 1 fila FK nativa
Conjuntos anidados Rango lft/rgt, muy rápido Reescribe media tabla Sin FK real
Adyacencia + path derivado Operador <@ sobre índice GiST 1 UPDATE + 1 sentencia FK nativa

Por eso nodes tiene parent_id como única fuente de verdad —con llave foránea real, ON DELETE RESTRICT y guarda anti-ciclo— y tres columnas derivadas que ningún proceso escribe a mano: las calcula el trigger trg_nodes_build_path en cada inserción y en cada movimiento.

REPORTES id=4 · path='4' · depth=0 ├─ Comercial id=17 · path='4.17' · depth=1 │ ├─ Colocaciones id=92 · path='4.17.92' · depth=2 │ └─ Mora de Cartera id=93 · path='4.17.93' · depth=2 │ └─ Descargar id=99 · path='4.17.93.99' · ACTION └─ Riesgos id=18 · path='4.18' · depth=1 └─ Cartera en Riesgo id=94 · path='4.18.94' · depth=2

Con esos derivados, las lecturas que antes exigían recursión se vuelven filtros indexados: el subárbol completo de un nodo es n.path <@ raiz.path, las migas de pan son esa misma comparación leída al revés, y el orden del menú es ORDER BY sort_path —sin ordenar nada en memoria.

Mover una rama

Es la operación que descarta a los conjuntos anidados. Reasignar parent_id dispara un trigger que reescribe los derivados de todos los descendientes en una única sentencia, sin recursión y sin tocar ningún otro nodo del árbol:

02_funciones_triggers.sql · fn_nodes_move_subtree
UPDATE seg.nodes c
   SET path      = NEW.path || subpath(c.path, nlevel(OLD.path)),
       depth     = (NEW.depth + nlevel(c.path) - nlevel(OLD.path))::smallint,
       sort_path = NEW.sort_path || substr(c.sort_path, length(OLD.sort_path) + 1)
 WHERE c.path <@ OLD.path
   AND c.id <> NEW.id;
Continuidad con el backend Ant. El legacy ya devuelve el menú como lista de adyacencia en list_sec, así que la migración es un mapeo directo de campos: cod_sec → code, cod_par → parent_id, desc_sec → name, act_sec → route, icon_sec → icon, order_sec → display_order.
04

Herencia: explícita por concesión

La herencia no es una propiedad del árbol sino de cada concesión. La columna applies_to lo decide fila por fila:

  • SUBTREE — el nodo y todos sus descendientes. Una fila cubre una carpeta entera, incluidos los reportes que se creen después.
  • NODE — exactamente ese nodo. Sirve para conceder un reporte suelto sin abrir la carpeta que lo contiene.

Reglas de resolución

Están implementadas una sola vez, en seg.fn_user_node_access, y las consumen tanto el menú como el guard del backend. Esa unicidad es deliberada: es lo que impide que la navegación y la autorización lleguen a decir cosas distintas.

R1

SUBTREE propaga hacia abajo; NODE no. La herencia se declara, no se asume.

R2

Gana la concesión cuyo nodo de origen es más profundo. La excepción explícita vence a la regla general.

R3

A igual profundidad, DENY vence a ALLOW.

R4

A igual profundidad, varios ALLOW suman sus banderas (bool_or): los roles de un usuario se acumulan, nunca se restan entre sí.

R5

Un rol con grants_full_access ve el árbol completo, sin necesidad de filas en node_permissions.

Si la política corporativa exige el modelo ACL clásico —una negación en cualquier nivel gana siempre, sin excepciones más profundas— basta sustituir un CTE de la consulta principal; la variante está escrita en 04_consultas_navegacion.sql como Consulta A'.

El caso que motivó la negación explícita

«El rol ve todo el sistema excepto la sección Seguridad» es una regla real del sistema heredado. Allí exigió una fila de permiso por cada módulo, generada por script. Aquí son dos filas:

03_seed_demo.sql

    -- Solo los nodos navegables tienen ruta.

    )

CREATE TABLE seg.node_permissions (
    id          BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    role_id     INTEGER     NOT NULL REFERENCES seg.roles(id) ON DELETE CASCADE,
    node_id     BIGINT      NOT NULL REFERENCES seg.nodes(id) ON DELETE CASCADE,

    grant_type  VARCHAR(5)  NOT NULL DEFAULT 'ALLOW',   -- ALLOW o DENY
    applies_to  VARCHAR(7)  NOT NULL DEFAULT 'SUBTREE', -- NODE = sin herencia

    can_view    BOOLEAN     NOT NULL DEFAULT TRUE,
    can_create  BOOLEAN     NOT NULL DEFAULT FALSE,
    can_update  BOOLEAN     NOT NULL DEFAULT FALSE,
    can_delete  BOOLEAN     NOT NULL DEFAULT FALSE,
    can_export  BOOLEAN     NOT NULL DEFAULT FALSE,

    is_active   BOOLEAN     NOT NULL DEFAULT TRUE,
    valid_until TIMESTAMPTZ,
    granted_by  BIGINT      REFERENCES seg.users(id) ON DELETE SET NULL,
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT node_permissions_uk        UNIQUE (role_id, node_id),
    CONSTRAINT node_permissions_grant_chk CHECK (grant_type IN ('ALLOW','DENY')),
    CONSTRAINT node_permissions_scope_chk CHECK (applies_to IN ('NODE','SUBTREE')),

    -- Una negacion es completa: no puede traer banderas en TRUE.
    CONSTRAINT node_permissions_deny_chk  CHECK (
        grant_type = 'ALLOW'
        OR NOT (can_view OR can_create OR can_update OR can_delete OR can_export)
    )
);

CREATE INDEX node_permissions_role_idx ON seg.node_permissions(role_id) WHERE is_active;

Trigger que mantiene el path

02_funciones_triggers.sql
-- En PostgreSQL los DEFAULT (incluida la columna IDENTITY) ya estan resueltos
-- cuando corre un trigger BEFORE INSERT: NEW.id esta disponible para el path.
CREATE OR REPLACE FUNCTION seg.fn_nodes_build_path() RETURNS trigger
LANGUAGE plpgsql AS $fn$
DECLARE
    v_parent seg.nodes%ROWTYPE;
    v_key    TEXT;
BEGIN
    v_key := lpad(NEW.display_order::text, 5, '0') || '-' || lpad(NEW.id::text, 12, '0');

    IF NEW.parent_id IS NULL THEN
        NEW.path := text2ltree(NEW.id::text);  NEW.depth := 0;  NEW.sort_path := v_key;
        RETURN NEW;
    END IF;

    SELECT * INTO v_parent FROM seg.nodes WHERE id = NEW.parent_id;

    -- Guarda anti-ciclo: un nodo no puede colgar de su propio descendiente.
    IF NEW.id = ANY (string_to_array(v_parent.path::text, '.')::bigint[]) THEN
        RAISE EXCEPTION 'Ciclo detectado: % no puede colgar de %', NEW.id, NEW.parent_id;
    END IF;

    NEW.path      := v_parent.path || NEW.id::text;
    NEW.depth     := (v_parent.depth + 1)::smallint;
    NEW.sort_path := v_parent.sort_path || '.' || v_key;
    RETURN NEW;
END;
$fn$;
06

La consulta: árbol autorizado en un viaje

Un solo WITH RECURSIVE resuelve las cuatro cosas que el menú necesita: qué roles tiene el usuario, hasta dónde llega cada concesión, quién gana en los conflictos y qué carpetas hay que añadir para que el árbol quede conectado.

04_consultas_navegacion.sql · Consulta A · $1 = users.id
WITH RECURSIVE
-- 1) Roles efectivos: directos + heredados del puesto ------------------------
roles_efectivos AS (
    SELECT ur.role_id
      FROM seg.user_roles ur
      JOIN seg.roles r ON r.id = ur.role_id AND r.is_active
     WHERE ur.user_id = $1
       AND ur.is_active
       AND ur.valid_from <= now()
       AND (ur.valid_until IS NULL OR ur.valid_until > now())
    UNION
    SELECT pr.role_id
      FROM seg.users u
      JOIN seg.position_roles pr ON pr.position_id = u.position_id AND pr.is_active
      JOIN seg.roles r           ON r.id = pr.role_id AND r.is_active
     WHERE u.id = $1 AND u.status = 'ACTIVE' AND u.deleted_at IS NULL
),

-- 2) Concesiones aplicables (+ bypass del superadministrador) ----------------
concesiones AS (
    SELECT np.node_id AS origen_id, np.grant_type, np.applies_to,
           np.can_view, np.can_create, np.can_update, np.can_delete, np.can_export
      FROM seg.node_permissions np
     WHERE np.role_id IN (SELECT role_id FROM roles_efectivos)
       AND np.is_active
       AND (np.valid_until IS NULL OR np.valid_until > now())
    UNION ALL
    SELECT n.id, 'ALLOW', 'SUBTREE', TRUE, TRUE, TRUE, TRUE, TRUE
      FROM seg.nodes n
     WHERE n.parent_id IS NULL
       AND EXISTS (SELECT 1 FROM roles_efectivos re
                     JOIN seg.roles r ON r.id = re.role_id
                    WHERE r.grants_full_access)
),

-- 3) Herencia hacia abajo: n.path <@ o.path = "n es o, o desciende de o" ----
alcance AS (
    SELECT n.id AS node_id, o.depth AS especificidad, c.grant_type,
           c.can_view, c.can_create, c.can_update, c.can_delete, c.can_export
      FROM concesiones c
      JOIN seg.nodes o ON o.id = c.origen_id
      JOIN seg.nodes n ON (c.applies_to = 'SUBTREE' AND n.path <@ o.path)
                       OR (c.applies_to = 'NODE'    AND n.id   =  o.id)
     WHERE n.is_active
),

-- 4) Precedencia: gana lo mas especifico; a igual nivel, la negacion vence ---
ganadoras AS (
    SELECT a.*, MAX(a.especificidad) OVER (PARTITION BY a.node_id) AS nivel_ganador
      FROM alcance a
),
resueltos AS (
    SELECT g.node_id,
           bool_or(g.grant_type = 'DENY') AS denegado,
           bool_or(g.can_view)   AS can_view,
           bool_or(g.can_create) AS can_create,
           bool_or(g.can_update) AS can_update,
           bool_or(g.can_delete) AS can_delete,
           bool_or(g.can_export) AS can_export
      FROM ganadoras g
     WHERE g.especificidad = g.nivel_ganador
     GROUP BY g.node_id
),
permitidos AS (
    SELECT * FROM resueltos WHERE NOT denegado AND can_view
),

-- 5) Cierre ascendente (RECURSIVO): las carpetas contenedoras del camino -----
--    UNION (no UNION ALL) corta la recursion al reconverger en un ancestro.
arbol AS (
    SELECT n.id, n.parent_id
      FROM seg.nodes n
      JOIN permitidos p ON p.node_id = n.id
     WHERE n.node_type <> 'ACTION'      -- las ACTION son permisos, no menu
       AND n.is_visible
    UNION
    SELECT padre.id, padre.parent_id
      FROM seg.nodes padre
      JOIN arbol a ON a.parent_id = padre.id
     WHERE padre.is_active AND padre.is_visible
)

SELECT n.id, n.parent_id, n.code, n.name, n.node_type, n.route, n.icon,
       n.depth, n.display_order, n.metadata, n.requires_mfa,
       CASE WHEN p.node_id IS NULL THEN 'CONTAINER' ELSE 'GRANTED' END AS access_source,
       COALESCE(p.can_create, FALSE) AS can_create,
       COALESCE(p.can_update, FALSE) AS can_update,
       COALESCE(p.can_delete, FALSE) AS can_delete,
       COALESCE(p.can_export, FALSE) AS can_export
  FROM arbol a
  JOIN seg.nodes n       ON n.id = a.id
  LEFT JOIN permitidos p ON p.node_id = n.id
 ORDER BY n.sort_path;   -- preorden exacto del menu, sin ordenar en memoria

Las dos filas CONTAINER son la razón de ser de la recursión: ninguna tiene concesión propia, pero sin ellas los reportes permitidos colgarían de la nada. REP_CARTERA aparece sin can_export porque su concesión NODE no incluyó esa bandera: el usuario ve el reporte, no puede descargarlo.

Variante portátil

ltree es específico de PostgreSQL. Si el MIS debe convivir con el Oracle del backend Ant, la Consulta B del mismo archivo usa solo parent_id y depth, propagando la herencia con un segundo término recursivo en lugar del operador <@. Se ejecuta igual en Oracle, SQL Server, MySQL 8+ y MariaDB 10.2+.

07

Lectura y operación

El contrato con el frontend no cambia

GET /api/v1/navegacion/arbol ejecuta la Consulta A y devuelve una lista plana ya ordenada. El servicio Node la convierte en JSON anidado en una pasada O(n) agrupando por parent_id en un Map —el mismo algoritmo que MenuStgService ya usa hoy contra list_sec, así que el front recibe la misma forma de datos que consume ahora.

Coste real

Con el volumen del MIS —unos 240 reportes, del orden de 400 nodos, ~30 roles y unos pocos miles de filas en node_permissions— todo cabe en memoria y la consulta responde en milisegundos. Las recomendaciones operativas son, en ese orden:

  1. Cachear el resultado por user_id con TTL corto (5 min), como ya hace AuthorizationService, e invalidar al cambiar roles o permisos.
  2. No materializar nada todavía. Una vista materializada mv_user_node_access solo se justifica por encima de ~5.000 nodos con ~10.000 usuarios.
  3. Autorizar siempre en el backend con seg.fn_user_can($1,$2,$3). El árbol que se envía al frontend es información de presentación, no un control de acceso.

Lo que el modelo deja preparado

  • Explicabilidad. La Consulta D devuelve la cadena rol → nodo de origen → alcance que concede o niega un acceso. Es lo que responde «¿por qué este usuario ve este reporte?» sin leer código.
  • Recertificación de accesos. La Consulta F da la matriz inversa —qué roles alcanzan un nodo y a cuántos usuarios afecta— que piden las revisiones periódicas de privilegios.
  • Caducidad automática. user_roles.valid_until y node_permissions.valid_until hacen que las coberturas temporales expiren solas, sin depender de que alguien recuerde revocarlas.
  • Sin IDs negativos. is_system y grants_full_access sustituyen el SSO_SUPERADMIN = -1 que el sistema heredado usa para no chocar con el autoincremento.
